# 成功大隊勤務看板

顯示當時段的人力、車輛編組與勤務類別，並整合 Google 行事曆行程。

---

## 這套東西怎麼運作

勤務資料鎖在需要登入的消防資訊系統（ttfd2.firemis.tw）裡。瀏覽器有安全機制，
**放在別的網站上的網頁沒辦法直接去抓它**。所以整套拆成三個角色：

```
[隊部電腦，人員已登入 ttfd2]
      │  點一下「更新看板」書籤
      │  在 ttfd2 自己的頁面裡讀取勤務表（同網域，合法）
      ▼
[Render 伺服器]  收下資料，存起來
      │
      ▼
[電視牆 / 手機 / 任何人開網址]   ← 不需要登入，自動更新
```

重點：**抓資料的動作發生在 ttfd2 自己的頁面裡**，所以拿得到；
看板端讀的是 Render 上的資料，所以不用登入。
帳號密碼全程不離開操作人員，不存在任何檔案或伺服器上。

**行事曆是另外一條完全獨立、不需要人操作的管線**：Google 日曆的
iCal 訂閱網址本身就是通行證，Render 伺服器自己每 12 小時去讀一次，
不用登入、不用書籤、不用隊部電腦開著。設定方式見下方部署步驟。

## 部署步驟

### 一、Render 建立服務

1. 把這個資料夾推上 GitHub
2. Render → New → Web Service → 連結該倉庫
3. 設定：
   - **Root Directory**：`server`
   - **Build Command**：`npm install`
   - **Start Command**：`npm start`
4. Environment 新增變數：
   - `PUSH_TOKEN`：自己取一串亂碼，採集器要用同一串
   - `ALLOW_ORIGIN`：`https://ttfd2.firemis.tw`
   - `CAL_ICS_URL_DAJI`（選填）：「大隊」來源日曆的 iCal 訂閱網址
   - `CAL_ICS_URL_YIXIAO`（選填）：「義消」來源日曆的 iCal 訂閱網址
   - `CAL_ICS_URL_JUBENBU`（選填）：「局本部」來源日曆的 iCal 訂閱網址
   - `CONFIG_PASSWORDS_URL`（選填）：密碼分頁發布出來的 CSV 網址
   - `CONFIG_DEPTS_URL`（選填）：單位代碼分頁發布出來的 CSV 網址
   - `CONFIG_NOTICES_URL`（選填）：跑馬燈分頁發布出來的 CSV 網址
   - `CONFIG_CALENDARS_URL`（選填）：行事曆分頁發布出來的 CSV 網址
     （跟上面 `CAL_ICS_URL_*` 是疊加關係，用來讓其他大隊自己上傳
     自己的行事曆，成功大隊現有的行事曆不用搬過去）

   行事曆那三個都是選填、互相獨立，沒設定就用看板內建的靜態快照。
   `CONFIG_*` 那四個也是選填、互相獨立，設定方式見
   `docs/試算表設定說明.md`（含預先整理好的單位代碼對照表，複製貼上
   即可）。
   拿 iCal 訂閱網址的方式：Google 日曆網頁版 → 該日曆「⋮」→
   設定和共用 → 往下捲到「整合設定」→ 複製「私人網址（iCal 格式）」
   （若該日曆本身已設成公開，也可以用「公開網址」，不含密鑰、風險
   較低）。**這個網址等同密碼，只貼進 Render 的環境變數，不要貼進
   任何會進版本庫的檔案或對話紀錄。**

部署完成後會拿到一個網址，例如 `https://duty-board.onrender.com`。

> Render 免費方案在 15 分鐘無人存取時會休眠，再次開啟約需 30 秒喚醒。
> 電視牆整天開著就不會休眠。

### 二、隊部電腦設定背景自動採集（現行做法，2026-11-09 起）

不用開瀏覽器分頁、不用書籤。電腦上用 Windows「工作排程器」每 30 分鐘叫起一個
看不見視窗的 Chrome，帶著事先登入好的 ttfd2 登入狀態，把全縣採集器
（`collector/collector-county.user.js`）塞進去跑一次，資料送到 Render 就關掉。
全縣 34 個單位的資料都由這一條管線送；成功大隊視角直接借用全縣資料，
不需要再另外跑成功大隊專屬採集器。

**需求**：Windows 電腦（要開機、且已登入 Windows）、Google Chrome、Node.js
（`C:\Program Files\nodejs`）。

**第一次設定**（只做一次，局本部帳號）：

1. 在 `collector\runner` 資料夾執行 `npm install`
2. 雙擊 `collector\runner\重新登入.bat`：跳出 Chrome 視窗 → 輸入看板網址
   與通行碼（通行碼就是 Render 環境變數 `PUSH_TOKEN` 那一串）→ 在視窗裡
   自己登入 ttfd2 → 程式偵測到登入後自動試跑一次，顯示「設定完成」
3. 工作排程器建立工作 `TTFD-Collector`：每 30 分鐘執行
   `collector\runner\run-collector.bat`（僅在使用者登入時執行）

登入資料存在 `collector\runner\profile\`、紀錄在 `collector\runner\logs\`，
兩者都已加進 `.gitignore`，**不會也不應該推上 GitHub**。

**檢查機制**（任何一層發現不對都看得到）：

| 層級 | 怎麼運作 |
|---|---|
| 採集電腦螢幕 | `runner.js` 每次跑完把結果記在 `logs\status-profile.json`。**登入過期**（結束代碼 2）立刻跳出訊息視窗，之後每約 2 小時再提醒；**其他失敗**連續 2 次才提醒，之後每約 2 小時再提醒；恢復正常會寫進紀錄。訊息用 Windows 內建 `msg` 送出，不會卡住排程 |
| 看板網頁 | 資料超過 **90 分鐘**沒更新，頁面上方告示改成「資料已 N 分鐘未更新，背景採集可能中斷…」（原本 5 小時，已縮短）。每分鐘檢查一次 |
| 紀錄檔 | `logs\run-YYYY-MM-DD.log`（每次採集過程）、`logs\scheduler-out.log`（排程輸出） |

收到「登入過期」提醒時：雙擊 `collector\runner\重新登入.bat`，看板網址與通行碼
直接按 Enter 沿用，重新登入 ttfd2 即可。登入狀態實際能撐多久尚未確定，
遇到過期請記下大約隔了多久。

**結束代碼**：0 成功；2 登入過期或登入資料夾不存在；3 採集失敗；4 逾時
（150 秒）；1 其他錯誤。

**電腦本身的盲點**：電腦關機、休眠、沒登入 Windows 時完全不會採集，這種情況
電腦自己發不出提醒。這一塊由下面的「外部監看」補上。

#### 外部監看：UptimeRobot（2026-11-09 設定完成並實測）

用免費的 UptimeRobot 每 5 分鐘從網路上「敲」一次看板伺服器，同時達成兩件事：
(1) 伺服器不會因 15 分鐘沒人連線而休眠；(2) 資料太久沒更新時寄 Email 通知。

**運作原理**：伺服器的 `/api/health` 加上 `maxAgeMin` 參數後，會檢查「全縣」與
「成功大隊」兩份資料中最新的一次收到時間。超過指定分鐘數、或根本沒有資料，就回
HTTP 503（異常）；否則回 200（正常）。不加參數時永遠回 200，只當作「伺服器醒著」
的探針。回傳內容有 `stale`（是否過期）與 `dataAgeMin`（資料幾分鐘前收到）。

**監看設定**（UptimeRobot 免費帳號）：

| 項目 | 設定 |
|---|---|
| 類型 | HTTP(s) |
| 網址 | `https://ttfd-duty-board.onrender.com/api/health?maxAgeMin=90` |
| 檢查間隔 | 5 分鐘（免費版最短） |
| 通知 | Email（轉成 Down 時寄一封，恢復時再寄一封） |

**實測結果（2026-11-09）**：故意把工作排程器的 `TTFD-Collector` 停用，資料過了
約 90 分鐘後 `/api/health` 轉 503，UptimeRobot 顯示 Down（`503`），Email 通知
成功寄達。重新啟用排程後，下一次採集成功，`/api/health` 回到 200（
`dataAgeMin` 0、34 個單位），整條通知與恢復流程驗證通過。

**要注意的事**：
- **重新部署後會有一小段 503**：部署完伺服器記憶體是空的，要等下一次採集
  （每小時 :23、:53）送資料進來才轉 200。這段期間收到一封 Down、之後一封
  恢復信是正常現象，不是故障。
- **Render 免費時數**：免費方案每月 750 小時是整個 Workspace 共用，且**只有
  Web Service 計入**（Static Site 不算）。看板這一個 Web Service 整月常開約
  744 小時（31 天），十二月只剩 6 小時餘裕。**不要再多開第二個免費 Web
  Service**，否則月底會被暫停。可到 Render 的 Billing／Usage 頁面查看已用時數。
- 通知對象是申請 UptimeRobot 帳號時填的 Email；要加人到 UptimeRobot 的
  「Alert Contacts」增加。

### 備用做法 A：書籤／Tampermonkey（舊做法，仍可用）

> 現行做法已改為上面的背景自動採集。以下保留作為備用。若同時開著舊的
> Tampermonkey／書籤採集器，資料會重複推送（無害，但沒必要）。

依 `collector/collector-bookmarklet.txt` 的說明，把書籤加到瀏覽器書籤列。
第一次點擊時會詢問 Render 網址與 `PUSH_TOKEN`，輸入後記在該台電腦。

### 備用做法 B：書籤版的日常使用

1. 隊部電腦早上登入 ttfd2
2. 開到勤務表列表頁，按一次「查詢」
3. 點一下「更新勤務看板」書籤
4. 狀態視窗保持開著，之後每 5 分鐘自動更新
5. 系統授權過期時狀態視窗會提示，重新登入後再點一次書籤

## 已知問題與待決定事項

### 伺服器重啟／休眠後，看板會暫時沒資料（2026-10-28 記錄；選項 1 已於 2026-11-09 完成）

> **進度**：選項 1（UptimeRobot 每 5 分鐘敲 `/api/health`）已完成，詳見上方
> 「外部監看：UptimeRobot」。休眠問題已解決，剩「重新部署那一下會空」。
> 選項 2 尚未做，視需要再決定。

**現象**：採集器狀態視窗偶爾出現「即時出勤更新失敗：尚未有完整資料，請先執行
一次完整採集」→「伺服器沒有完整資料（可能剛重新啟動），改為立即執行一次完整
採集…」。

**原因**：Render 免費方案兩種情況會清空伺服器記憶體（資料只存記憶體＋
`/tmp` 暫存檔，`/tmp` 重啟後也會消失）：(1) 超過 15 分鐘沒有任何連線就休眠，
醒來是全新啟動；(2) 重新部署。伺服器空的時候，採集器的「快速推送」（只帶即時
出勤）會被拒絕（409），這是設計如此。

**目前已有的緩解（v13 起）**：採集器遇到 409 會立刻自動補跑一次完整採集，通常
一分鐘內補回，這段訊息本身是「自動補救在運作」，不是資料傳不出去。

**還剩的缺口**：伺服器休眠後若是「看板先被打開」，在採集器下一次推送之前
（最久 30 分鐘），看板會停在沒資料／內建範例狀態。

**已評估過的選項**（使用者還在考慮，尚未動工）：
1. **讓伺服器不休眠（建議先做，零程式改動）**：用免費監測服務（如 UptimeRobot）
   每 5 分鐘打一次 `/api/health`。一個免費服務整月常開約 744 小時，在 Render
   免費額度 750 小時內（注意：同一帳號若還有其他免費服務會共用這個額度）。
   只剩「重新部署」那一下會空，採集器會自動補回。
2. **資料存到免費雲端小資料庫（想更保險再做）**：例如 Upstash Redis。伺服器
   收到推送時順便存一份、開機時讀回來，休眠或部署都不怕空。需使用者申請免費
   帳號並設兩個環境變數，程式要改 `server.js`。實測全縣資料約 150 KB，在
   Upstash 免費版單次請求 1 MB 的上限內。
3. **採集器資料先寫進 Google 試算表、看板再去讀（評估後不建議）**：試算表一格
   最多 5 萬字元，150 KB 要切很多格；「發布到網路」的內容更新有數分鐘延遲，
   即時出勤不再即時；採集器無法直接寫試算表，需另外做 Google Apps Script
   當中繼站（多一個網址／密鑰、有執行次數上限）；勤務人員名單與即時出勤會變
   成「知道連結就能讀」的公開試算表連結。

**待決定**：選項 1 已完成；要不要再做選項 2（讓重新部署也不空）？

## 開發者備註

`collector/collector.js` 是可讀版；改完後用下列指令重新產生書籤字串：

```bash
python collector/build.py collector/collector.js collector/_min.txt
```

不要用正則 `/\*.*?\*/` 移除區塊註解 —— 程式碼字串裡若含 `*/`（例如 `*/*`）
會被誤判為註解結尾，把中間整段吃掉。`build.py` 已改為逐行判斷。
